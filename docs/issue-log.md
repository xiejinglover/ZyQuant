# 问题与踩坑记录

本文沉淀 2026-07-26 ~ 2026-07-28 期间在「全量数据采集 → 数据发布 → 红利低波 V1.7
策略复现 → 因子层下沉」这条链路上暴露出的全部缺陷、误判与实测结论。

每条按「现象 / 根因 / 修法 / 验证 / 教训」记录。带 ✅ 的已修复并有回归测试，
带 ⚠️ 的是尚未处理或已知限制。

## 一、数据层真实 Bug（Hermes 归一化）

这一组的共同特点：**单元测试全绿，只有真实数据能暴露**。夹具都是「字段齐全、
分布均匀」的理想数据，而真实缺陷全部来自「某个字段在某个年份之后突然全空」这类
供应商行为变化。

### 1.1 ✅ 停牌日缺涨跌停价被误判为核心字段缺失

- **现象**：全量采集失败，25353 行被隔离，其中 22934 行 `missing_core_market_field`、
  2419 行 `unexplained_missing_bar`。
- **根因**：`_build_market()` 把 `LIMIT_UP_PRICE` / `LIMIT_DOWN_PRICE` 列为核心字段。
  但停牌日供应商**不发布涨跌停价**（该日不可交易，价带无意义），于是每个停牌日
  都被判为脏数据丢弃，日历随即报缺 bar。
- **修法**：`hermes_normalize.py:1024`，价带只在**可交易日**强制要求：

  ```python
  missing_band = (
      source["LIMIT_UP_PRICE"].isna() | source["LIMIT_DOWN_PRICE"].isna()
  )
  core_missing = bad_price | (missing_band & ~source["paused"].astype(bool))
  ```

  同时 `contracts.py` 中 `limit_up` / `limit_down` 改为 `nullable=True`。
- **安全性论证**：执行层在读 `limit_up/limit_down` **之前**就已按 `paused` 拒单，
  停牌日价带为空不改变任何成交结果。
- **教训**：「核心字段」的判定必须带上状态维度。字段缺失有两种性质——
  *数据质量问题* 与 *该状态下本就无定义*，混为一谈会误杀真实行情。

### 1.2 ✅ 分红公告日字段自 2020 年起全空 → 99.5% 分红事件被丢弃

- **现象**：`corporate_actions` 仅 17814 行，2018 年后几乎没有分红记录。
- **根因**：`_build_actions()` 用 `PUBLISH_DATE`（董事会预案日）作为可见日。
  该字段供应商已停止填充：2019 年 81% 为空，**2020 年起 100% 为空**。
  可见日为空 → 事件永远不可见 → 被丢弃。
- **修法**：`hermes_normalize.py:605` 改用 `IM_PUBLISH_DATE`（分红实施公告日），
  全历史 0% 空值，且**没有任何一行晚于除权日**（已逐行核查）。
  按用户要求，2019 年之前的历史**也一并改用同一字段**，全历史一个定义。
- **验证**：`cash_dividend` 17814 → 46299 行。差额 1145 行恰好等于
  `PER_CASH_DIV` 为空的纯送股事件数，账对得上。
- **教训**：任何 PIT 可见性字段上线前必须做**逐年空值率扫描**，而不是看整体空值率
  ——整体 30% 空值可能意味着「近 6 年 100% 空」。

### 1.3 ✅ 股息率取了每年 1–4 月会塌陷的字段

- **现象**：策略候选池在每年 1–4 月骤降。2016-01-29 只有 5 只股票通过
  「股息率 > 3%」筛选。
- **根因**：`_build_valuation()` 用 `DIV_RATE_TTM`。该字段在年报披露季
  （1–4 月）因分子口径切换而**塌陷 95%**。
- **修法**：`hermes_normalize.py:1218` 改用 `DIV_RATE_L12M`（近 12 月滚动股息率），
  仍 `/100.0` 做百分比 → 比率换算。
- **验证**：2016-01-29 候选池 5 → 106 只。
- **教训**：同名指标的不同口径（TTM vs L12M）在 A 股财报季行为差异巨大。
  选字段时必须画**逐月覆盖率曲线**，季节性塌陷一眼可见。

### 1.4 ✅ 缺少 PIT 的 ST 状态（前视偏差）

- **现象**：策略无法做 ST 过滤，只能用当前股票名判断，构成前视偏差。
- **根因**：快照里没有任何带 `known_at` 的 ST 状态表。
- **修法**：
  - `hermes.py` 新增源表 `equ_inst_sstate`（含 `SECURITY_ID_TABLES` 与
    `DATE_FILTERS["equ_inst_sstate"] = "EFF_DATE <= %s"`）；
  - `contracts.py` 新增 `special_treatment` 契约表，进入 `DYNAMIC_TABLES`
    与 `PRIMARY_KEYS`，并通过新增的 `OPTIONAL_TABLES` 声明为可选；
  - `_build_special_treatment()` 逐状态迁移转写为一个窗口，
    `known_at = PUBLISH_DATE`，缺失时回落 `EFF_DATE`。
- **偏差量化**：2015-12-31 时点 PIT ST 数 61 只。若改用「当前股票名含 ST」过滤，
  会**误剔 417 只当时干净的股票**、**误留 36 只当时是 ST 的股票**。
- **教训**：所有状态类数据（ST、行业、指数成分、停复牌）都必须转写为
  带 `known_at` 的窗口表，不能靠「最新快照」反推历史。

### 1.5 ✅ 退市代码残留记录导致日历报缺 bar

- **现象**：换代码上市的标的（000043 中航善达 → 001914 招商积余）留下一条退市记录，
  日历要求它在整个「上市期」每天都有 bar。
- **根因**：供应商对代码变更保留两条 instrument 记录，其中旧代码那条永远拿不到行情。
- **修法**：新增 `_drop_superseded_aliases()`，判据为**该 `SECURITY_ID` 在
  `mkt_equd` 中一根 bar 都没有**。
- **踩坑点**：我最初打算用 `PARTY_ID` 识别别名记录。**先核查后发现这会误删
  600087 退市长油的 1068 根真实 bar**——真实的退市重新上市
  （600087 退市长油 → 601975 招商南油）同样共享 `PARTY_ID`，但它自己拥有行情。
- **教训**：删除判据必须是「该记录不可能有数据」这类**充分条件**，
  不能是「看起来像重复」这类相关性特征。改动前先跑一遍反例扫描。

## 二、框架性能与正确性缺陷

### 2.1 ✅ `metric_panel` 逐日全表扫描（阻断性性能缺陷）

- **现象**：日频财务因子面板预估需 5 小时，完全不可用。
- **根因**：`snapshot.py` 的 `metric_panel` 对每个日期调一次 `latest_metrics`，
  每次都完整读一遍 `fundamental_metrics` 并 groupby（实测 4.5 秒/日期）。
  ~4000 个交易日 → ~5 小时。这也是 `FactorContext.fundamentals` 的 `dates`
  默认只传两个端点的原因。
- **语义陷阱（关键）**：`latest_metrics` 的排序键是
  `(fiscal_period_end, available_at, metric_id)`——**报告期优先于可见日**。
  所以**不能**简单对 `available_at` 做 `merge_asof`：一份晚公告的旧期重述，
  `available_at` 更晚但 `fiscal_period_end` 更早，`latest_metrics` 会选
  *报告期更新* 的那条。
- **修法**：`_as_of_steps()` 单次读表 + 向量化 as-of：
  `eligible = max(available_at, fiscal_period_end)` → 对复合键做全局字典序 rank →
  分组 `cummax` → `drop_duplicates(keep="last")` → 逆置换映射回原行。
  `metric_panel()` 在其上重写（长表形态不变），并新增
  `metric_matrix(dates, metric_code, basis, instruments=None)` 直接产出宽表。
- **验证（真实数据）**：**1558.8 秒 → 52.7 秒（29.6×）**，
  1670697 行**逐行完全一致**。宽表 25.0 秒，形状 (59, 2907)，非空率 99.5%。
- **改动前已备份**：`.backup/20260727-220850/`。
- **教训**：as-of 语义的排序键必须逐字段确认。这里如果照直觉写 `merge_asof`，
  在「重述」场景下会静默取错值，且正常数据上完全测不出来。

### 2.2 ✅ 成本模型硬门禁 `backtest_ready: False`

- **现象**：`market_rules` 缺费率字段直接导致回测拒绝启动。
- **根因**：`engine.py` 有一条 `backtest_ready is False` 硬门禁。但费率本身
  就是**用户可指定项**，数据缺失不应阻断回测。
- **修法**（用户选定「缺失即用默认值」）：
  - `market.py` 新增 `COST_FIELDS`、`DEFAULT_MARKET_COSTS`
    （股票：佣金 2.5bp / 最低 ¥5 / 卖出印花税 5bp / 买入 0 / 过户费 0.1bp；
    ETF：印花税与过户费为 0）与 `resolve_costs()`；
  - 逐字段回落链：`config_scalar → config_override → market_rules → default`，
    同时返回 `provenance`（每个字段的来源）；
  - `engine.py` 去掉硬门禁，`market_rule()` 查表包在
    `try/except DataContractError` 中，`BacktestResult` 新增
    `cost_model={"rates":…, "provenance":…}`。
- **教训**：数据门禁只该拦「不可替代的事实」（价格、日历）。
  可由用户配置的参数缺失时，正确做法是**取默认值并记录来源**，而不是拒绝运行。

## 三、因子层 Bug

### 3.1 ✅ 财务因子向退市/未上市标的输出值

- **现象**：用户追问「怎么因子值的行数还不一样」。财务因子行数
  **多于**行情类因子（16.28M vs 14.5M），与直觉相反。
- **根因**（两条）：
  1. `instruments` 表中有 **977 只孤儿标的**（无任何行情）；
  2. 财务面板的前向填充**没有终止边界**，退市后继续按最后一期财报填值，
     产生 **754706 行（4.6%）落在上市窗口之外**。
- **修法**：`cn_equity.py:56` 新增 `_restrict_to_listed()`，
  用 `instruments.list_date` / `delist_date` 做 inner join 后裁剪：
  `stamp >= _listed and (_delisted.isna() or stamp < _delisted)`。
  在 4 处调用点接入（第 103/251/495/535 行）。
- **验证**：`net_profit_ytd` 16285777 → 14312603 行。
- **教训**：`ffill` 用在时间序列上时**必须显式给出终止条件**。
  「最后一个已知值一直有效」这个假设对退市标的直接错误。

### 3.1b ✅ 修复后的退市股抽查结果（2026-07-28）

读**本次重建产物** `runs/factors/panel.parquet`（14,522,000 行）核对：

| 检查项 | 结果 |
|---|---|
| 上市日之前的行数 | **0** |
| 退市日及之后的行数 | **0**（修复前 754,706） |
| `instruments` 表查不到的标的 | **0**（修复前 977） |
| 落在非交易日的行数 | **0** |
| `(日期, 标的)` 重复行 | **0** |
| 六列全为 NaN 的行 | **0** |
| 276 只退市标的中面板缺失的 | **0** |
| 面板末日与退市日的缺口 | 中位 **0**、最大 **0** 交易日 |

逐股抽查（覆盖 2014/2015/2019/2022 四个退市年份）行数与日历完全对齐，例如
600087 退市长油日历内应有 1068 个交易日：零回溯的三个财务因子与股息率各 1068 行，
Beta 816 行（= 1068 − 252 预热），动量 929 行（= 1068 − 139 预热）。

### 3.2 ⚠️ 抽样方法本身出过错：按文件大小挑缓存文件

- **现象**：修复 3.1 之后抽查 000024.XSHE（2015-12-30 退市）与 600087.XSHG
  （2014-06-05 退市），仍看到退市后有行（beta 231 行、momentum 20 行、
  net_profit 2566/2952 行），看似修复无效。
- **根因（方法错误，非代码错误）**：因子源码哈希变了 → 铸出新 cache key，
  缓存目录里**同时存在修复前与修复后两份 parquet**。我按
  `os.path.getsize` 取「最大文件」，取到的是**旧文件**。
  旁证：`net_profit_ytd` 显示 4020 行、末日 2026-07-24，与修复前行为完全吻合；
  而重建日志自己报的是 `rows=14,312,603`。
- **正确抽样方式**：读**本次重建刚写出的** `runs/factors/panel.parquet`，
  而不是从缓存目录里按大小猜文件。
- **顺带确认了两个正常项**：beta 首值 2011-01-18（253 交易日预热）、
  momentum 首值 2010-07-30（140 交易日预热），都符合预期。
- **教训**：内容寻址缓存目录是**累积**的，不是当前状态。
  验证必须锚定「本次运行的产物路径」或「本次运行返回的 cache_key」。

### 1.6 ⚠️ 未修复：`equ_div_pit` 的修订行未去重，分红被重复计入

抽查因子面板尾部时顺带发现，属于数据层，尚未修复。

- **现象**：`corporate_actions` 中有 34 组 `(instrument_id, ex_date, event_type)`
  重复（0.15%），涉及 31 只标的。
- **根因**：`equ_div_pit` 是 **PIT 表——分配方案的每次修订都是一行新记录**，
  由 `ANNO_ID` / `UPDATE_TIME` 区分；一次分配的真实身份是
  `(SECURITY_ID, END_DATE, EVENT_NUM)`。`_build_actions()` 逐行转写，没有按这个
  身份去重，于是同一次分红被写成多个事件。
  按 `(SECURITY_ID, END_DATE, EVENT_NUM)` 统计原始表：**20 组 / 40 行重复**，其中
  - **15 组是纯重复**：金额、除权日全同，只有 `ANNO_ID` / `UPDATE_TIME` 不同
    （如 000048 的 END_DATE 2024-06-30、EVENT_NUM 0514、¥0.38 出现两次，
    公告时间 2024-09-12 与 2024-09-23）；
  - **5 组是真修订**：金额或除权日被改过，两个版本都被写了进去。
    最严重的是 002129——¥0.10 的除权日从 2023-05-26 改到 2023-06-16，
    结果**同一笔分红在两个日期各派一次**；600157 同型（2024-08-26 → 2024-11-15）；
    003001 / 301097 / 688320 是金额小幅重算。
- **必须区分的合法情形（不能一起去重）**：同一除权日上确实可能有**两笔不同的分配**，
  它们的 `END_DATE` / `EVENT_NUM` 不同，两笔都是真的：
  - 000738 在 2013-06-14 同时派 2012 年报的 ¥0.021（0503）与 2013-04-18 期的
    ¥0.041（0504）；
  - 002043 在 2026-06-01 同时派 2025 年报的 ¥0.132（0523）与 2026Q1 的 ¥0.180（0524）。

  所以**去重键必须是 `(SECURITY_ID, END_DATE, EVENT_NUM)` 且保留
  `UPDATE_TIME` 最新的一行**，绝不能按 `(instrument_id, ex_date)` 去重。
- **影响面（两处都会吃到）**：
  - `engine.py:743` 按唯一 `event_id` 逐事件派现
    （`amount = quantity * cash_per_share`）→ 持有者被**重复派息**；
  - `adjustment.py:147` 在 `(code, ex_date)` 内 `cash += cash_value`
    → 自算复权因子被抬高（v3 用厂商因子，但自算值仍参与交叉校验）。
  - 契约层抓不到：主键是 `event_id`，而它是唯一的。
- **实际影响量**：除权日范围 2019-06-06 ~ 2026-06-08，落在回测期内 34 组；
  与 ST 版回测持仓的交集只有 **000048 一只**（纯重复型，多派 ¥0.38/股）。
  短区间硬验证锚点（2015-12-10 → 2016-06-30）不受影响——最早的重复在 2019 年。
- **修复需要重建 `corporate_actions` 并发布 v4**，因此留待决策。

## 四、契约与测试夹具问题

### 4.1 ✅ 夹具违反契约 `fiscal_period_end < available_at`

- **现象**：新写的 as-of 测试报错。
- **根因**：我构造的夹具让报告期晚于可见日，被 `validation.py:249` 拒绝。
- **修法**：修正夹具；并把那个「不可能状态」的测试**改写为断言契约会拒绝它**。
- **教训**：夹具也必须过契约校验。构造不出来的状态就不是需要处理的状态，
  该测的是「契约拦住了它」。

### 4.2 ✅ 夹具日期与被测区间不相交

- **现象**：`metric_matrix` 返回 `(3, 0)`。
- **根因**：夹具的 `available_at` 是 2015-04-30，而测试的日期区间在 2014-10 结束。
- **修法**：把报告期/可见日改为**相对 `days` 生成**，不再写死。
- **教训**：夹具里的日期一律相对生成，绝不硬编码绝对日期。

### 4.3 ✅ 缺口测试把缺失日放在了回归窗口之外

- **现象**：动量「窗口内缺 1 天必须为 NaN」的测试通过不了（其实是没测到）。
- **根因**：夹具 200 天，我把缺口放在 `days[40]`，而实际回归窗口是 `days[60:180]`。
- **修法**：缺口移到 `days[100]`。
- **教训**：写边界测试时先把**实际生效的窗口下标算出来**，再放缺口。

### 4.4 ✅ 多进程 worker 无法 pickle 闭包

- **现象**：`PicklingError: Can't pickle local object`。
- **根因**：`ProcessPoolExecutor` 需要 pickle 可调用对象，闭包不行。
- **修法**：模块级 `_run_worker` 蹦床函数 + 通过 fork 继承的 `_WORKER` 全局。
- **教训**：项目内已有先例（`hermes_normalize.py`），新写并行代码先照抄惯例。

### 4.5 ✅ `positions` 帧没有 `price` 列

- **现象**：AttributeError。
- **根因**：列名是 `last_price` / `market_value`。
- **修法**：改用 `market_value`。

## 五、并行与向量化：实测结论（重要的否定型经验）

三次都是用户质疑后**实测推翻了我原来的方案**，这些数字应当作为后续优化的依据。

### 5.1 ❌ 线程并行无效（GIL 绑定）

| 方式 | 加速比 | 并行效率 |
|---|---|---|
| 4 线程 | **0.83×（更慢）** | — |
| 8 线程 | **0.77×（更慢）** | — |
| 2 进程 | 1.86× | 93% |
| 4 进程 | 3.69× | 92% |
| 8 进程 | 4.93× | 62%（本机仅 10 核） |

瓶颈在 Python 层（逐股 `pd.concat` + `dropna`），不在 numpy 的 C 计算，
所以线程只会增加开销。**必须走进程**，并把 `OMP_NUM_THREADS` /
`OPENBLAS_NUM_THREADS` / `MKL_NUM_THREADS` 固定为 1 防线程超订。

### 5.2 ❌ 放弃向量化重写（成本不值得换风险）

实测单格成本：momentum 45.4 µs、beta 180.0 µs → 全面板单进程 10 分钟 + 41 分钟。
按日期分片多进程后落在十分钟内，**向量化带来的收益不足以抵消正确性风险**。

向量化版本我已实证可行（`sliding_window_view` + `einsum`，
2600 × 5800 规模 2.7 秒 / 2.1 GB，与循环版 NaN 位置完全一致、有值处相对误差 1e-15），
但风险集中在一处：

> **Beta 的分母随个股变化**（已数值验证：一只股票缺 4 天，分母相对差 5.26e-03），
> 因为所有加权和都在「个股与市场同时有效」的子集上求，每只股票的缺失日不同。
> **掩码逻辑写错时，全有效的测试用例完全发现不了。**

### 5.3 ⚠️ 我曾错误宣称「Beta 可以简化」

用户质疑「这东西怎么能简化啊」，实测后**承认判断错误**：Beta 的分母是
个股相关的，不可简化。只有动量存在真实的简化空间（120 天全有效要求使掩码恒为全 1，
x 侧量退化为常数，斜率分母恒为 83743591.25）。

### 5.4 日后若真要向量化，验证清单

- `Sw/Sx/Sxx/Sy/Sxy` + 有效计数共 6 个固定核滚动和，`einsum` 一次算完；
- 展开式已验证：`beta = (Sxy − Sx·Sy/Sw) / (Sxx − Sx²/Sw)`，相对误差 1e-16；
- 对拍必须覆盖：**带散落缺失日**、观测数正好 20 与正好 21、窗口中途上市的标的；
- `np.polyfit(x, y, 1, w=W)` 等价于权重 `W²` 的加权 OLS（误差 1e-15），
  而 R² 用线性 `W` 且以**未加权均值**中心化——**原文这处不对称必须保留**；
- 指数核 O(1) 递推不必做（误差 4.9e-14，但直接卷积已足够快）。

## 五之二、因子取值的极端尾部：已逐个溯源（都不是计算错误）

抽查面板尾部时的三处极端值，逐个查到根因，结论是**因子算得对，但用的时候有陷阱**。

### A. Beta 尾部 `|beta| > 5`：674 行（0.005%），67 只标的

**98.5% 是上市不满两个月的新股**，从上市到出现极端值的自然日数中位仅 **34 天**
（华之杰 603400 上市后 31 天 |beta|=13.88；无线传媒 301551 上市后 36 天 13.54）。

根因是 `minimum_observations=21` 配在 252 日窗口上——上市 21 个交易日的新股就能出
一个 Beta。这是从聚宽原策略继承的门槛，**不是 bug**。对低波策略本身无害
（这种 Beta 排在最差端会被剔掉），但它**参与横截面分位的计算**，会挤压其余标的的分位。

### B. 动量尾部：>20 的有 21617 行（0.16%），最大值 3272.84

溯源 000622 恒立退 2013-05-27：回归窗口 2012-10-25 ~ 2013-04-24 的 120 天里，
**前约 80 天该股全程停牌**（`paused=True`、`volume=0`、收盘冻结在 1.12），
2013-02 复牌后跳到 4.69。于是「120 天全有效」的要求被**冻结价**满足了，
未加权对数斜率 0.0308/日 → 年化 2220 倍。
（顺带确认 2013-02-08 的 10 送 20 复权正确：因子 2.52548 → 7.57644，恰好 ×3.0。）

关键判定：**动量因子不屏蔽停牌日**（Beta 屏蔽，`cn_equity.py:199`
`returns.mask(self.paused, 0.0)`）。但聚宽原策略取价用的正是
`skip_paused=False, fill_paused=True`（原文 `_get_price_frame_in_batches`），
**行为完全一致**，所以这是忠实复现，不是偏差。

**真正的策略风险**：动量只剔尾部 31%，长期停牌后复牌的股票会拿到**最高**的动量分位。

### C. 股息率尾部：振东制药 300158 的 0.56 是真的

2022-05-09 除权，`cash_per_share = 2.70`，当时股价约 ¥5 —— 一次极端的特别分红。

顺带把这个字段做了一次全市场对拍：**厂商 `dividend_yield` vs 自算「近 12 月现金分红
÷ 不复权收盘」**，四个抽样日（2016/2019/2022/2025）比值中位数都是 **1.0000**，
且「厂商 >0.5% 而自算无分红事件」与「自算 >0.5% 而厂商为 0」**都是 0 例**。

5% 分位上厂商偏低的那些，原因全部查清了——**厂商会按后续送转重述每股分红，
自算的朴素求和不会**：

| 标的 | 送转 | 比值 |
|---|---|---|
| 星华新材 301077 | 2022-05-25 送 1.0 | 0.5006 |
| 奥士康 002913 | 2022-05-20 送 1.0 | 0.500 |
| 迅游科技 300467 | 2015-09-29 送 3.0 | 0.247（= 1/4）|

**结论**：1.3 的修复（改用 `DIV_RATE_L12M`）经全市场验证正确；并且这条对拍还证明了
一件更强的事——**不要用 `corporate_actions` 手搓股息率**，因为它没有做送转重述。

### D. ROE 符号陷阱：204369 行（1.41%）、955 只标的，净利为负而 ROE 为正

`roe_ytd = net_profit_parent(ytd) / equity_parent(instant)`。**所有者权益为负**时
负÷负 = 正，于是资不抵债的公司拿到极高的正 ROE：
宝鹰股份 002047 净利 −¥7.44 亿 → ROE **121.14**；雏鹰退 002477 净利 −¥11.38 亿 → ROE **105.75**。

数学上没错，但**任何按 ROE 分位排序的质量筛都会把资不抵债的公司排在最前**。
本策略的 `net_profit > 0` 硬门会把它们挡在选股之外，可**分位是在硬门之前算的**
（见下节第 1 条），所以它们仍然在扭曲其他标的的分位——这一点与聚宽一致，
复现无偏差，但作为因子使用者必须知道。

## 六、策略复现中的语义陷阱

这些不是 bug，是**必须精确复现才能对上净值**的语义细节，写下来防止后人「优化」掉。

1. **分位在硬门之前算**：质量模块（`net_profit` 硬门 + OCF 0.7 + roe 0.3）的
   横截面分位是在**门禁筛选之前**算的；动量剔尾 31% 的分位同样在**剔除之前**固定。
   顺序反了结果就不同。
2. **稳定排序**：并列时按代码 `mergesort` 稳定排序。
3. **后复权价对动量无影响（已证明）**：前后复权价相差一个**每股常数** →
   对数空间里是加性常数 → 斜率与 R² 不变（实测相对误差 < 1e-12）。
4. **时点等价**：聚宽在 D-1 决策、D 开盘成交；ZyQuant `next_open` 在 T 决策、
   T+1 开盘成交 ⇒ **T = D-1**，所以月度信号应落在**上月最后一个交易日**。
5. **80% 仓位的表达**：写成 `sum(weights) == 0.8`。`cash_weight` 只是账本元数据
   （`engine.py:263,284`），不参与下单。
6. **动量权重的不对称性**：见 5.4 第 4 条。

## 八、诊断方法论：我犯过的错

单独列出来，因为这些错误的代价比代码 bug 更高——它们会把后续工作引到错误方向。

|---|---|
